# Extension packs — delivery, lifecycle, and independence

Research for [#2099](https://github.com/bible-on-site/bible-on-site/issues/2099);
input to the removal/state work in
[#2098](https://github.com/bible-on-site/bible-on-site/issues/2098).
Every claim below is traced to code or packaging configuration.

The store-side payloads are produced at packaging time: `prepare_perushim_assets.py`
installs a paired catalog+notes artifact (CI `app-package.yml`), and
`prepare_recitation_assets.py --platform {Android|iOS|Windows}` writes the packs,
the dataset `Contents.json` ODR tags, and the bundled catalog. Release artifacts are
checked by `verify_recitation_assets.py` (AAB modules/manifests, IPA
`OnDemandResources.plist` tags + compiled `Assets.car`, MSIX archives).

## Install paths

- **Commentary** (`PerushimNotesService`): `InitializeAsync` copies the DB into
  `AppDataDirectory` whenever the OS pack is already delivered — no user action and
  no download needed. `TryDownloadNotesAsync` (Preferences button) additionally
  calls `FetchAsync` (PAD `AssetPackManager.Fetch` / ODR
  `NSBundleResourceRequest.BeginAccessingResources`), then validates the copied DB
  against the bundled catalog (`perush_catalog` mapping snapshot, or matching
  `build_timestamp` for legacy packs) before marking it available.
- **Recitation** (`RecitationService.DownloadAsync`): resolves the selected
  perakim to `RecitationBookPack`s, obtains each zip from the delivered pack or
  `FetchAsync`, verifies zip SHA-256 + size + exact entry inventory against the
  bundled catalog, then extracts each missing track to
  `AppDataDirectory/extensions/recitation/{audioSha256}.mp3` with per-file hash
  verification and atomic rename. Completed chapters survive cancellation.
- **Debug/desktop fallback**: when delivery yields no path, both services read the
  payload from the app package (`TryCopyFromAppPackageAsync` / the bundled zip
  branch in `InstallBookAsync`). Store Release builds never bundle these payloads.

## Update behavior

All pack data is **app-release-coupled**: catalogs are bundled with the app and
pack bytes are compiled into the AAB/IPA for that version. There is no independent
server-side pack update channel.

- App update → store delivers updated packs (PAD packs and ODR tags version with
  the app; Play re-downloads changed packs automatically).
- Commentary: `TryUpgradeFromPadAsync` compares `build_timestamp` on every init and
  replaces the local DB when the store copy is newer. The bundled catalog is
  refreshed by hash comparison on every `PerushimCatalogService.InitializeAsync`.
- iOS extracted ODR copies are generation-scoped
  (`Caches/odr_assets/{version}-{build}/{pack}`), so an updated app re-extracts the
  new payload instead of trusting the old file. Prior-generation directories are
  left behind for the OS to purge — the app never cleans them.
- Recitation: `UpdateAsync` re-reads the bundled catalog; `DownloadAsync` reuses
  local MP3s whose `audioSha256` still matches and re-extracts only books whose
  archive changed. Word timings live in the bundled catalog, so timing changes ride
  app releases without re-downloading unchanged audio. Superseded MP3s (old
  `audioSha256` names) are currently **orphaned on disk** — nothing collects them.

## Removal behavior (current reality)

There is **no removal API anywhere** — this is #2098's scope. What the platforms
allow:

- Android PAD has no pack-deletion API (`AssetPackManager` exposes `Cancel`,
  `Fetch`, `GetPackLocation(s)`, listeners — no remove). Pack bytes are
  Play-managed and are reclaimed only on app uninstall.
- iOS ODR has no force-delete; `EndAccessingResources` only makes the tag
  purgeable when the OS needs space.
- App-owned copies **can** be deleted: the commentary DB in `AppDataDirectory`,
  `extensions/recitation/*.mp3`, and the `odr_assets` cache dirs.
- **Trap for #2098** (verified by `ExtensionPackLifecycleTests`): deleting the
  commentary DB is silently undone — `InitializeCoreAsync` re-copies it from the
  still-installed store pack on the next init (the reader page and preferences
  invoke init). A deliberate removal needs a persistent tombstone honored by init,
  not just file deletion.
- Recitation removal is clean: init and `UpdateAsync` load catalog metadata only
  and never re-download audio, so deleted MP3s stay deleted until `DownloadAsync`.

## Independence assessment

Delivery is independent per pack — each is its own PAD module / ODR tag, fetched
and cached separately (`StoreDeliveryDownloadsWholeSelectedBook` verifies
recitation never fetches `perushim_notes`). Independence of **versioning** does
not exist by design:

- Commentary notes must match the bundled catalog (mapping snapshot or shared
  `build_timestamp`) — a mismatched pack is rejected as unavailable.
- Recitation zips must match the bundled catalog hashes; playable audio must also
  match the bundled Bible text (`TextSha256`), so a text-changing app update
  invalidates installed audio.
- `RecitationService.IsInstalled` means "catalog loaded" — true on every properly
  packaged release even with zero audio. It cannot drive the three-state summary
  in #2098; that must be computed from `HasAudio` file state.

## Verified vs. not verified

Unit-level (CI, mocked `IPadDeliveryService`): install permutations, per-book
scope, cancellation/resume, corrupt-pack rejection, update reuse, restart/offline
use, removal semantics — `RecitationServiceTests`, `PerushimNotesServiceTests`,
`NotesDeliveryTests`, `OdrCacheTests`, `PerushimAttributionTests`, and
`ExtensionPackLifecycleTests`.

Not exercised anywhere:

- Real PAD `Fetch` transitions on device (listener callbacks, `WaitingForWifi`
  dialog, post-fetch polling). Feasible on an emulator only through a
  `bundletool --local-testing` AAB harness — not wired into CI; the mobile-e2e
  Debug APK always takes the bundled fallback, so PAD code never runs there.
- Real iOS ODR download/purge (requires a TestFlight/App Store install; cannot be
  tested on the simulator or from Windows). CI verifies only IPA manifest/payload
  presence via `verify_recitation_assets.py`.
- OS-level storage reclamation after a future removal feature (both stores keep
  their copies regardless of what the app deletes).
