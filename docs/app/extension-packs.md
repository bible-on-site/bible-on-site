# Extension packs — delivery, lifecycle, and independence

Researched in [#2099](https://github.com/bible-on-site/bible-on-site/issues/2099);
the removal/state work below was implemented for
[#2098](https://github.com/bible-on-site/bible-on-site/issues/2098).
Every claim is traced to code or packaging configuration.

## Inventory

| Pack | Payload | Android | iOS / Mac Catalyst | Windows |
| ---- | ------- | ------- | ------------------ | ------- |
| Commentary notes | `sefaria-dump-5784-sivan-4.perushim_notes.sqlite` | PAD asset pack `perushim_notes`, `DeliveryType="OnDemand"` (`BibleOnSite.csproj`); Debug also bundles it as `MauiAsset` | Apple-hosted managed asset pack `perushim-notes` — `Platforms/iOS/AssetPacks/perushim-notes/` (payload + `Manifest.json`) archived by `xcrun ba-package`; Debug bundles it as `MauiAsset` since local/simulator builds cannot fetch a store-hosted pack | MSIX **optional package** `perushim_notes` (`Platforms/Windows/ExtensionPacks/perushim_notes/` — notes DB + prebuilt search index) delivered as a durable Store add-on when configured, else the `app-v*` release-payload HTTPS fallback; Debug bundles the directory as `MauiAsset` |
| Commentary catalog | `sefaria-dump-5784-sivan-4.perushim_catalog.sqlite` (~40 KB) | **Bundled** `MauiAsset` — always installed, refreshed by `PackagedDatabase.RefreshAsync` on hash change | Same | Same |
| Recitation catalog | `recitation-catalog.json` (generated by `app/devops/prepare_recitation_assets.py`, gitignored) | **Bundled** `MauiAsset`; required at release build (`RequireRecitationExtensionAssets`) | Same | Same |
| Recitation audio, per sefer | `recitation_{seferId}.zip` of sha-named MP3s (hyphenated on iOS and in MSIX identity names — see note below) | PAD asset pack `recitation_{seferId}`, `DeliveryType="OnDemand"`; Debug also `MauiAsset` | managed asset pack `recitation-{seferId}` via generated `Platforms/iOS/AssetPacks/recitation-*/` (gitignored) — payload + `Manifest.json` → `.aar` | MSIX **optional package** `recitation_{seferId}` (`Platforms/Windows/ExtensionPacks/recitation_{seferId}/`, gitignored) — one `{pack}.msix` per sefer under `.artifacts/extension-packs`, durable Store add-on or release-payload HTTPS fallback; Debug bundles packs as `MauiAsset` |

Pack identifiers differ per platform because the stores impose disjoint
charsets: Play asset-pack names take alphanumerics and underscores (`recitation_1`),
while App Store Connect accepts only alphanumerics and hyphens (`recitation-1`).
The iOS pack directory, manifest `assetPackID`, `.aar` filename, and the
`PackName` the app passes to `BAAssetPackManager` all carry the hyphenated form.
Windows keeps the pack directory names (`recitation_1`, `perushim_notes`) and
hyphenates only the MSIX **identity name** — `54181DoradSoft.929-.recitation-1` —
because Appx identity names match `[-.A-Za-z0-9]+` (no underscores); the same
rule also caps identity names at 50 characters.

For Windows the packaging pipeline (`GenerateWindowsExtensionPacks` in
`app/devops/Build.Package.cs`, also invocable standalone via
`dotnet run --project devops -- PackageWindowsExtensionPacks`) turns every
staged pack directory into an **MSIX optional package**: a generated
`AppxManifest.xml` declaring `uap3:MainPackageDependency` on the base package
identity, the `StoreLogo.png` recovered from the just-built base MSIX, and the
payload files at the package root — packed by `makeappx` into
`.artifacts/extension-packs/{pack}.msix` and signed with the same certificate
thumbprint as the base package when `--certificate-thumbprint` is provided.
Every raw payload — the recitation `.zip` archives and the perushim `.sqlite`
pair — is additionally staged flat under `.artifacts/payloads` and published
as `app-v*` release assets — the HTTPS fallback bytes for sideloaded or
Store-unconfigured installs (a Windows-only release has no iOS leg to carry
the `.sqlite` pair; when both legs publish, the iOS staging carries identical
bytes under identical asset names). `extension-packs.json5` ships in the
base MSIX and binds each pack name to a Partner Center StoreId (plus an
optional `packageName` override) once the durable add-ons are created — until
then the runtime never attempts a Store install for that pack.

The store-side payloads are produced at packaging time: `prepare_perushim_assets.py`
installs a paired catalog+notes artifact (CI `app-package.yml`), and
`prepare_recitation_assets.py --platform {Android|iOS|Windows}` writes the packs,
the per-pack `Manifest.json` files, and the bundled catalog. For iOS, the raw
payloads are additionally staged flat under `.artifacts/payloads` and published
as plain `app-v*` release assets — that is the HTTPS delivery source for
runtimes where managed packs cannot exist (see below). Release artifacts are
checked by `verify_recitation_assets.py` (AAB modules/manifests, IPA embedded
downloader extension, per-pack `Manifest.json`/source-payload match, `.aar`
extracted via `aa` and hashed against the catalog, staged release payload match;
on Windows: a payload-free base MSIX, per-pack optional `.msix` identity +
`MainPackageDependency` + publisher match, payload hashes against the catalog,
and the staged fallback payloads). The same verification emits `asset-packs.json` — the verified
pack plan recording each pack's `Manifest.json`, per-file SHA-256 map,
content fingerprint, and archive digest — which rides the release beside the
`.aar` files. The `.aar` files are published to App Store Connect separately
from the IPA (`cd-app.yml`, `xcrun altool --upload-asset-pack` on an Xcode 26+
toolchain) — see reuse below.

The perushim pack also carries `sefaria-dump-5784-sivan-4.hebrew_search.sqlite`,
the prebuilt FTS5 index the device never rebuilds (#2222). Since #3309 its
`notes_documents` table stores only each note's identity (perek, pasuk, perush,
sefer, `note_idx`); hit bodies resolve from the compressed `note_blob` rows in
the notes DB instead of duplicating ~250 MB of commentary text inside the
index. `SearchIndexService` still reads the older fat layout when a legacy pack
or cached index supplies it, and swaps a fat working index for the slim file
once the pack redelivers. `audit_android_aab_size.py` gates the packaged AAB on
this layout plus on-demand delivery for every asset pack, an optional-payload
allowlist inside `base/`, and a compressed-size budget per module.

## Install paths

- **Commentary** (`PerushimNotesService`): `InitializeAsync` copies the DB into
  `AppDataDirectory` whenever the OS pack is already delivered — no user action and
  no download needed. `TryDownloadNotesAsync` (Preferences button) additionally
  calls `FetchAsync` (PAD `AssetPackManager.Fetch` / Background Assets
  `BAAssetPackManager.EnsureLocalAvailability`), then validates the copied DB
  against the bundled catalog (`perush_catalog` mapping snapshot, or matching
  `build_timestamp` for legacy packs) before marking it available.
- **Recitation** (`RecitationService.DownloadAsync`): resolves the selected
  perakim to `RecitationBookPack`s, obtains each zip from the delivered pack or
  `FetchAsync`, verifies zip SHA-256 + size + exact entry inventory against the
  bundled catalog, then extracts each missing track to
  `AppDataDirectory/extensions/recitation/{audioSha256}.mp3` with per-file hash
  verification and atomic rename. Completed chapters survive cancellation.
- **Windows** (`PadDeliveryService`, `#if WINDOWS`): `TryGetAssetPathAsync`
  first probes `Package.Current.Dependencies` for an already-installed
  optional package whose identity matches the pack (`extension-packs.json5`
  `packageName` override, else `{mainPackage}.{pack-hyphenated}`) and resolves
  the payload inside its install location (`EffectivePath`, `InstalledPath` on
  older builds; `StorageFolder`/`StorageFile` copy when plain file IO cannot
  reach it). `FetchAsync` consults the bundled `extension-packs.json5` map: a
  pack with a configured StoreId installs through
  `StoreContext.RequestDownloadAndInstallStorePackagesAsync` (progress from
  `PackageDownloadProgress`, which spans the download+install phases), then
  re-probes the dependencies. Packs without a StoreId — and unpackaged runs,
  Store failures, or `Package.Current` unavailability — take the HTTPS
  release-payload leg: `{file}` downloads from the `app-v{version}` release
  into the generation-scoped `asset_packs/{version}-{build}` cache through a
  `.download` temp + atomic rename, shared with the iOS fallback code path.
- **Debug/desktop fallback**: when delivery yields no path, both services read the
  payload from the app package (`TryCopyFromAppPackageAsync` / the bundled zip
  branch in `InstallBookAsync`). Store Release builds never bundle these payloads.

## Update behavior

All pack data is **app-release-coupled**: catalogs are bundled with the app, and
pack bytes ride the same release (inside the AAB for Android; as Apple-hosted
`.aar` archives for iOS). There is no independent server-side pack update
channel — but on iOS the *pack version* is not app-build-coupled: unchanged
payloads reuse the existing App Store Connect version instead of minting a new
one (see "Release-time pack reuse" below).

Managed Background Assets require **iOS 26 / macOS 26** — plus the app-group
entitlement, which unsigned simulator/dev builds lack. On runtimes without
managed delivery `FetchAsync` instead downloads the same pack payloads over
HTTPS from the `app-v{version}` GitHub release (they are release assets beside
the `.aar` files) into the same generation-scoped extraction cache, so
`TryGetAssetPathAsync` and the install paths are identical on either leg. Each
payload is streamed through a `.download` temp file with atomic rename — an
interrupted fetch never leaves a partial file the next probe would serve —
and every listed payload is required: the perushim pack pairs its notes DB
with the prebuilt search index, which the device never rebuilds (#2222), so a
release missing either file fails the fetch instead of caching a half-payload
the completeness probe would refuse to serve.

- App update → store delivers updated packs (PAD packs and Apple-hosted asset
  packs both re-download changed packs automatically; on iOS only the packs
  whose content actually changed received a new App Store Connect version — see
  reuse below).

## Release-time pack reuse (implemented for #2794)

Apple asset-pack **versions** are independent resources: a version stays live on
its distribution channel (internal TestFlight, external TestFlight, App Store)
until a newer version supersedes it there. Rebuilding the app therefore does not
require re-uploading unchanged packs — Apple serves the existing version to new
builds on the same channel. The deploy keeps that property deliberately:

| Platform | What repeats every release | What is reused |
| -------- | -------------------------- | -------------- |
| iOS (Apple-hosted) | `ba-package` archives are rebuilt and the plan re-verified every package run; the deploy step always re-queries App Store Connect | Pack **versions** and uploads are skipped per pack whose live version provably carries the same bytes; only changed packs upload |
| Android (PAD) | Every AAB embeds all required `perushim_notes`/`recitation_*` modules — PAD has no independent pack releases | Nothing is omitted; unchanged zips are just identical module contents inside the new AAB |
| Windows | Every package run rebuilds `{pack}.msix` optional packages bound to the new base identity version and re-stages the fallback payloads | Store-side: durable add-ons are independent products — a re-published app does not re-push unchanged pack content through Partner Center; device-side unchanged packs stay installed across app updates (related-set updates only re-download changed optional packages) |
| GitHub fallback | Every `app-v*` release republishes `.aar`, plan, and raw payload assets for older-runtime HTTPS delivery | Not applicable — old-release assets are never deleted or relocated |

The mechanism, end to end:

1. **Verified plan** (`verify_recitation_assets.py` → `asset-packs.json`):
   each pack's fingerprint combines its `Manifest.json` bytes with the sorted
   per-file SHA-256 list — a schema/manifest change, a notes-DB or
   search-index change (perushim ships both in one pack), or a single changed
   audio byte shifts exactly that pack's identity. Archive timestamps and app
   version numbers do not participate.
2. **Publish decision** (`asset-pack-upload.mjs`): the deploy restores the plan
   with the `.aar` assets, re-hashes every archive against the recorded digest
   (a swapped archive aborts before any API call), then for each pack reads
   App Store Connect — pack record, all versions, and the `ASSET` upload-file
   checksums of the live (newest `COMPLETE`) version plus anything in flight.
   Reuse requires *all* of: live version exists, its checksum (or a prior
   receipt's version+content tie) matches this pack, and its internal beta
   release is `READY_FOR_TESTING`. The receipt tie compares Apple's checksum
   to the receipt's producer archive proof *in the algorithm Apple reports* —
   SHA-256 or MD5 — because rebuilt `.aar` containers are not byte-identical
   even over identical content. Proven differences — missing pack, a receipt
   tying the live version to other content, wrong platform — upload a fresh
   version. Remote bytes that are *unverifiable* (checksum differs or is absent
   with no receipt tie) upload only when receipt evidence is complete: a
   finished empty search is the explicit bootstrap path, but a discovery
   failure (spawn/`ENOBUFS`, `gh` error, incomplete history, malformed
   receipt) blocks the publish instead of justifying uploads on missing
   evidence. A version without a resource id blocks the publish before any
   upload.
3. **Idempotent reconciliation**: a `PROCESSING` version already carrying our
   bytes is waited out and reconciled, never duplicated — interrupted runs
   converge on the next attempt (a stranded `AWAITING_UPLOAD` reservation has
   no bytes yet, so it is simply superseded by a fresh upload). Decisions for
   the whole fleet are made before the first upload.
4. **Verification**: every pack — reused, reconciled, or uploaded — ends at the
   same proof: the live version carries our bytes and is ready for internal
   testing. The step reports `uploaded / reused / reconciled / blocked` per
   pack; "reused" is never reported as "uploaded".
5. **Publication receipt** (`asset-pack-publication.json` on the release):
   per pack it records the content fingerprint, the producer archive proof
   (SHA-256 *and* MD5 of the bytes the recorded Apple version carries —
   chained across reuses from the original producing release, never the
   current run's rebuilt container), Apple pack and version ids/numbers, all
   three channel release linkages, the action taken, and
   `producedBy`/`consumedBy` provenance — so a reused pack's original
   producer release stays visible and a later deploy can prove reuse even when
   Apple exposes no checksum for a version. Discovery scans release pages via
   `gh api --jq` (bounded output regardless of payload size — #2842 ENOBUFS),
   distinguishes *no receipt exists* (bootstrap) from *receipt unreadable*
   (blocked), and never synthesizes a receipt after a failed read. Read-only
   App Store Connect lookups retry transient timeout/network and
   throttling/5xx answers inside a bounded budget; permanent 4xx or malformed
   answers fail immediately.

Release-side consequences that must keep holding:

- An app-only milestone (no payload change) performs zero `altool` uploads and
  creates zero new pack versions; a one-book recitation change uploads exactly
  one `.aar`.
- The receipt's `versionId` tie is the fallback when Apple withholds upload
  metadata — content equality is never inferred from a pack identifier, a
  version number, or "latest" alone.
- Older app builds on the same channel keep working: publishing a changed pack
  version supersedes only that pack's channel pointer, and the on-device
  generation-scoped extraction (`asset_packs/{version}-{build}`) re-extracts
  instead of trusting stale files.
- Commentary: `TryUpgradeFromPadAsync` compares `build_timestamp` on every init and
  replaces the local DB when the store copy is newer. The bundled catalog is
  refreshed by hash comparison on every `PerushimCatalogService.InitializeAsync`.
- iOS extracted asset-pack copies are generation-scoped
  (`Caches/asset_packs/{version}-{build}/{pack}`), so an updated app re-extracts the
  new payload instead of trusting the old file. Prior-generation and legacy unversioned directories
  are deleted on the next access so pack payloads (hundreds of MB) never
  accumulate.
- Recitation: `UpdateAsync` re-reads the bundled catalog; `DownloadAsync` reuses
  local MP3s whose `audioSha256` still matches and re-extracts only books whose
  archive changed. Word timings live in the bundled catalog, so timing changes ride
  app releases without re-downloading unchanged audio. `UpdateAsync` also sweeps
  `extensions/recitation` files the current catalog does not reference —
  superseded `audioSha256` MP3s and aborted `*.download` fragments — while a
  download in progress holds its gate and is never collected.

## Removal behavior (implemented for #2098)

Platform limits (unchanged):

- Android PAD has no pack-deletion API (`AssetPackManager` exposes `Cancel`,
  `Fetch`, `GetPackLocation(s)`, listeners — no remove). Pack bytes are
  Play-managed and are reclaimed only on app uninstall.
- iOS managed packs can be removed with `BAAssetPackManager.RemoveAssetPack`;
  the system may also evict a downloaded pack under storage pressure.
- Windows optional packages are separate MSIX installs: the user can remove a
  pack from Settings → Apps (or `Remove-AppxPackage`) without touching the app;
  the next `TryGetAssetPathAsync`/`FetchAsync` simply reports the pack as
  undelivered and installs or downloads it again. Release-payload cache copies
  under `asset_packs/{version}-{build}` are app-owned and swept like iOS.
- App-owned copies **can** be deleted: the commentary DB in `AppDataDirectory`,
  `extensions/recitation/*.mp3`, and the `asset_packs` cache dirs.
- **Trap for #2098** (verified by `ExtensionPackLifecycleTests`): deleting the
  commentary DB is silently undone — `InitializeCoreAsync` re-copies it from the
  still-installed store pack on the next init (the reader page and preferences
  invoke init). A deliberate removal needs a persistent tombstone honored by init,
  not just file deletion.
- Recitation removal is clean: init and `UpdateAsync` load catalog metadata only
  and never re-download audio, so deleted MP3s stay deleted until `DownloadAsync`.

## Independence assessment

Delivery is independent per pack — each is its own PAD module / asset pack, fetched
and cached separately (`StoreDeliveryDownloadsWholeSelectedBook` verifies
recitation never fetches the notes pack). Independence of **versioning** does
not exist by design:

- Commentary notes must match the bundled catalog (mapping snapshot or shared
  `build_timestamp`) — a mismatched pack is rejected as unavailable.
- Recitation zips must match the bundled catalog hashes; playable audio must also
  match the bundled Bible text (`TextSha256`), so a text-changing app update
  invalidates installed audio.
- `RecitationService.IsInstalled` means "catalog loaded" — true on every properly
  packaged release even with zero audio. The three-state summary is computed from
  `InstallState`/`HasAudio` file state, never from `IsInstalled` or the playback
  on/off preference.

## Windows Store setup (Partner Center)

Windows delivery ships in two layers and only the first needs Partner Center:

1. **Optional packages** (`{pack}.msix` under `.artifacts/extension-packs`) are
   signed with the app certificate and bound to the base package by
   `uap3:MainPackageDependency` + matching publisher — a Store submission that
   includes them makes them installable parts of the related set.
2. **Durable add-ons** give `StoreContext` a product to install on demand. In
   Partner Center → app → Add-ons, create one durable add-on per pack
   (`recitation-1` … `recitation-39`, `perushim-notes`), submit it with the
   corresponding optional package, then record the assigned StoreId in
   `app/BibleOnSite/Platforms/Windows/extension-packs.json5`:
   `"recitation_1": { "storeId": "9XXXXXXXXXXX" }`. An add-on whose package
   identity differs from the `{mainPackage}.{pack-hyphenated}` convention also
   records `"packageName"`.

Until a pack has a StoreId the runtime never calls Store APIs for it — it
downloads the same payload bytes from the `app-v{version}` release assets, so
shipping add-ons is an incremental roll-out rather than a hard switch.

Known limits of the Store leg: `StoreContext` needs a Store-signed install, so
sideloaded MSIX and unpackaged debug always take the HTTPS fallback;
`RequestDownloadAndInstallStorePackagesAsync` reports combined
download+install progress only; and optional-package content is version-locked
to the app release it was built against (related-set updates re-download packs
whose payload changed — the catalog-hash check in `InstallBookAsync` remains
the authority on what counts as "changed").
